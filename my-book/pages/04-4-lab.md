# 04-4. 4단원 실습과 평가

## 실습 A: 상태 전이표

이메일 사용자가 거치는 상태를 표로 완성한다.

| 상태 | Auth 사용자 | Email confirmed | Session | 화면 행동 |
|---|---:|---:|---:|---|
| 가입 전 | 없음 | 해당 없음 | 없음 | 가입 폼 |
| 가입 후 확인 전 | 있음 | 아니오 | 보통 없음 | 메일 확인 안내 |
| 확인 후 로그인 전 | 있음 | 예 | 없음 | 로그인 폼 |
| 로그인 성공 | 있음 | 예 | 있음 | 메인 이동 |
| 로그아웃 | 있음 | 예 | 없음 | 로그인 이동 |

이 표를 이용하면 “Users 목록에 있으니 로그인 상태다”라는 잘못된 생각을 고칠 수 있다.

## 실습 B: 코드 흐름 추적

회원가입 모드에서 `signUp`이 성공했지만 `data.session`이 없다고 가정한다. 실행되는 줄을 순서대로 적는다.

1. `setLoading(true)`
2. `signUp`
3. `if (error)` 통과
4. `if (!data.session)` 진입
5. 인증 메일 안내 toast
6. `return`
7. `finally`의 `setLoading(false)`

`return`을 했는데도 `finally`가 실행된다는 점이 중요하다. 따라서 버튼이 영원히 loading 상태로 남지 않는다. 공통 `navigate("/")`는 실행되지 않는다.

## 실습 C: Auth와 프로필 비교

Authentication → Users와 Table Editor → `public.users`를 각각 연다. 같은 계정의 UUID가 같은지 비교한다. Provider와 email confirmed는 Auth에서, display name과 앱용 추가 정보는 public 프로필에서 관리한다.

프로필 upsert가 실패해도 Auth 로그인이 성공했을 수 있다. 앱이 두 작업을 한 덩어리처럼 안내하면 원인 구분이 어려워진다. 운영에서는 프로필 저장 오류를 따로 기록하고 재시도 전략을 설계할 수 있다.

## 형성평가

1. `signUp`과 `signInWithPassword`의 차이를 쓰시오.
2. `try/catch/finally`에서 `finally`가 필요한 이유를 예로 설명하시오.
3. Google Provider 계정에 임의의 비밀번호로 Email 로그인을 할 수 있다고 단정하면 안 되는 이유는 무엇인가?
4. `upsert`와 `insert`의 차이를 쓰시오.
5. 로그인 직후 무한 이동이 생기는 조건을 의사코드로 표현하시오.

## 확장 과제

비밀번호 재설정 버튼을 설계하되 다음을 포함한다: 이메일 입력 검증, Supabase 재설정 메일 요청, 허용된 redirect URL, 새 비밀번호 화면, 성공 후 세션 처리, 과도한 요청 제한 안내. 실제 구현 전 공식 Supabase 문서의 현재 메서드를 확인한다.
