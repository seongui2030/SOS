# 06-4. AI와 안전하게 개발하기

## 좋은 요청의 다섯 요소

1. 목표: 무엇을 완성할지
2. 범위: 어떤 파일과 기능인지
3. 제약: 수정 금지 파일, 유지할 기능
4. 증거: 오류 문장, 재현 순서, 상태 코드
5. 검증: 어떤 명령과 사용 시나리오로 확인할지

예를 들어 `로그인이 안 돼`보다 다음 요청이 좋다.

```text
localhost:8080/auth에서 Email 계정으로 로그인하면
Invalid login credentials가 표시됩니다. Authentication Users에는
계정이 있고 Provider는 Email입니다. 파일을 먼저 읽어 원인을 설명하고,
수정이 필요하면 auth.tsx만 수정한 뒤 TypeScript 검사를 실행해 주세요.
```

## 설명, 진단, 수정의 차이

`설명해 줘`는 보통 파일 변경 권한을 뜻하지 않는다. `원인을 진단해 줘`도 원인과 증거를 찾는 단계다. 실제 변경을 원하면 `수정해 줘` 또는 `완성본을 만들어 줘`라고 말한다. AI가 의도하지 않은 범위를 바꾸지 않았는지 diff를 본다.

## 작업 전후 순서

```powershell
git status
git diff
```

작업 전에는 기존 변경을 기록한다. AI 작업 후에는 다시 실행하고 변경된 파일과 줄을 검토한다.

```powershell
npx tsc --noEmit
npm run lint
npm run build
```

검사 통과는 오류가 전혀 없다는 증명이 아니라, 검사 범위의 문제를 찾지 못했다는 뜻이다. 실제 회원가입, OAuth, DB 저장을 브라우저에서도 시험한다.

## AI 답변을 검증하는 질문

- 이 설명은 현재 설치된 버전에 맞는가?
- 공식 문서나 실제 파일이 근거인가?
- 비밀 키를 브라우저 코드에 넣지 않았는가?
- 오류 처리가 성공 경로를 깨뜨리지 않는가?
- RLS가 다른 사용자의 접근을 실제로 막는가?
- 배포 후 환경변수 재빌드가 필요한가?

## 비밀정보 처리

`.env.local`을 통째로 붙이지 않는다. 질문에는 이름만 쓰고 값을 `YOUR_KEY`로 바꾼다. 토큰을 노출했다면 대화 삭제만 믿지 말고 발급 서비스에서 폐기·재발급한다. AI가 출력한 로그에도 비밀이 포함될 수 있어 공유 전에 가린다.

## Git 체크포인트

공식 OpenAI 문서도 작업 전후 Git 체크포인트를 권한다. 작은 목적 단위로 커밋하면 문제가 생겼을 때 변경 이유를 찾고 되돌리기 쉽다. 이미 원격에 올린 역사를 강제로 다시 쓰기보다 새로운 수정 커밋을 만든다.

```powershell
git add -A
git status
git commit -m "Fix email confirmation flow"
git push origin main
```

커밋 메시지는 결과가 드러나게 쓴다. `update`보다 `Fix email confirmation flow`가 나중에 이해하기 쉽다.

## 종합 수행평가

다음 과정을 보고서로 제출한다.

1. 새 브랜치 또는 안전한 실습 저장소를 준비한다.
2. Codex에게 프로젝트 구조 설명을 요청한다.
3. 작은 UI 또는 오류 처리 개선을 한 가지 요청한다.
4. 제안된 diff에서 유지할 변경을 선택한다.
5. TypeScript, lint, build를 검사한다.
6. 브라우저 Network로 기능을 시험한다.
7. 작업 전후 차이와 AI 답변에서 직접 검증한 내용을 기록한다.
