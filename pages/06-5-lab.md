## 최종 프로젝트 시나리오

팀은 이메일과 Google 로그인을 제공하는 긴급출동 비서를 Vercel에 배포한다. 각 팀원은 개발자, 데이터베이스 담당, 배포·보안 담당 역할을 맡고 서로의 결과를 검토한다.

## 1단계: 배포 전 증거 수집

```powershell
git status
git diff --stat
npx tsc --noEmit
npm run lint
npm run build
```

각 명령의 종료 결과를 기록한다. 기존 사용자 변경을 임의로 지우지 않는다. `.env.local`이 staging에 나타나면 커밋하지 말고 `.gitignore`와 과거 추적 여부를 확인한다.

## 2단계: 설정표 작성

실제 비밀 값 대신 마지막 네 글자만 확인표에 기록한다.

| 설정 | 로컬 | Vercel Production | 서비스 화면 |
|---|---|---|---|
| Supabase URL project ref | 확인 | 확인 | Supabase |
| Publishable key 일치 | 확인 | 확인 | Supabase |
| Service role 노출 없음 | 확인 | Secret | Supabase |
| 앱 운영 도메인 | 해당 없음 | 확인 | Supabase/Google/Kakao |
| Google callback | 해당 없음 | 해당 없음 | Google |

## 3단계: 기능 시험

1. 시크릿 창에서 운영 주소를 연다.
2. 새 Email 계정을 가입한다.
3. 이메일 확인 전 안내가 맞는지 본다.
4. 인증 링크 후 로그인한다.
5. 대화가 생성되는지 본다.
6. 로그아웃하고 Google로 로그인한다.
7. 사용자 A와 B의 데이터가 RLS로 분리되는지 본다.
8. Network에서 4xx/5xx 요청을 기록한다.

## 4단계: Codex 검토 요청

```text
현재 변경 내용을 코드 리뷰해 주세요. 인증 우회, service role key의
브라우저 노출, 무한 리디렉션, RLS와 맞지 않는 user_id 저장을 중점적으로
찾아 주세요. 먼저 읽기 전용으로 보고하고 파일은 수정하지 마세요.
```

보고서를 읽은 뒤 근거가 맞는 항목만 별도 수정 요청으로 보낸다. AI가 “문제가 없다”고 해도 실제 두 계정 시험을 생략하지 않는다.

## 문제 해결 구술 평가

교사는 다음 중 하나를 제시한다.

- Google 로그인 400 Unsupported provider
- 로그인 후 conversations 404 반복
- 운영에서만 Supabase 환경변수 누락
- Email 가입자는 있으나 로그인 실패
- SQL 함수 실행 시 no language specified

학생은 오류가 발생한 단계, 가장 먼저 확인할 화면이나 파일, 하지 말아야 할 불필요한 조치, 재시험 방법을 설명한다.

## 최종 성찰

완성된 웹 앱은 코드만으로 만들어지지 않는다. 브라우저, 빌드 도구, 인증 공급자, 데이터베이스, 배포 서버가 주소와 권한으로 연결된다. 오류를 잘 해결하는 개발자는 무작정 설정을 바꾸지 않고 실패한 단계를 찾는다. AI는 이 탐색을 빠르게 돕지만, 실제 프로젝트와 로그를 근거로 판단하고 결과에 책임지는 일은 개발자의 몫이다.
