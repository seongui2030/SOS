## 05. 데이터베이스 스키마와 RLS

### 학습 목표

- 테이블, 행, 열, 기본 키, 외래 키를 설명할 수 있다.
- SOS의 여섯 public 테이블 관계를 읽을 수 있다.
- RLS가 필요한 이유와 정책의 `USING`, `WITH CHECK`를 구분한다.

관계형 데이터베이스는 정보를 표로 나누고 키로 연결한다. 한 표에 모든 내용을 넣으면 이메일이나 이름이 메시지마다 반복되고 수정이 어려워진다. SOS는 사용자 프로필, 건강 정보, 대화, 메시지, 긴급 연락처, 긴급 알림을 분리한다.

```text
auth.users
 ├─ public.users
 ├─ healths
 ├─ conversations ─ messages
 ├─ emergency_contacts
 └─ emergency_alerts
```

기본 키는 한 행을 유일하게 찾는 값이다. 이 프로젝트는 대부분 UUID를 사용한다. 외래 키는 다른 표의 기본 키를 가리킨다. `messages.conversation_id`가 `conversations.id`를 가리키는 것이 예다.

DB 구조만 맞아도 보안이 자동으로 해결되지는 않는다. 웹 브라우저는 publishable key로 직접 Supabase API를 호출하므로 RLS가 사용자별 접근을 제한한다. 정책이 `auth.uid() = user_id`를 검사하면 로그인 사용자 ID와 행의 소유자 ID가 같을 때만 허용된다.

### 스키마를 설계하는 질문

1. 무엇을 한 행으로 볼 것인가?
2. 행을 유일하게 찾는 키는 무엇인가?
3. 다른 표와 어떤 관계인가?
4. 삭제될 때 연결된 데이터는 어떻게 할 것인가?
5. 누가 읽고, 추가하고, 수정하고, 삭제할 수 있는가?
6. 자주 검색하거나 정렬하는 열은 무엇인가?

### 확인 문제

1. 기본 키와 외래 키의 차이는 무엇인가?
2. 한 대화에 여러 메시지가 연결되는 관계를 무엇이라고 하는가?
3. publishable key를 쓰는 브라우저 앱에서 RLS가 중요한 이유는 무엇인가?
