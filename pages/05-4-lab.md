## 실습 A: 관계 읽기

다음 SQL에서 부모와 자식, 삭제 동작을 설명한다.

```sql
conversation_id uuid NOT NULL
  REFERENCES public.conversations(id)
  ON DELETE CASCADE
```

`conversations`가 부모, `messages`가 자식이다. 대화가 삭제되면 연결된 메시지도 삭제된다. 반대로 메시지 하나를 삭제해도 대화가 자동 삭제되지는 않는다.

## 실습 B: 안전한 연락처 테이블

아래 SQL을 읽고 각 제약의 목적을 주석으로 적는다.

```sql
CREATE TABLE public.practice_contacts (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL DEFAULT auth.uid()
    REFERENCES auth.users(id) ON DELETE CASCADE,
  name text NOT NULL CHECK (length(btrim(name)) > 0),
  phone text,
  enabled boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

실제 프로젝트에 실행하지 않고 연습용 SQL로 읽는다. 실행한다면 개발 DB에서 하고 정리 계획을 세운다.

## 실습 C: RLS 공격 시나리오

사용자 A가 브라우저 요청의 `user_id`를 사용자 B의 UUID로 바꿔 insert한다고 가정한다.

```sql
CREATE POLICY "insert_own"
ON public.practice_contacts
FOR INSERT TO authenticated
WITH CHECK (auth.uid() = user_id);
```

현재 로그인 토큰의 UID는 A인데 새 행의 user_id는 B이므로 조건이 거짓이다. DB가 요청을 거부한다. 화면에서 user_id 입력칸을 숨기는 것만으로는 이런 공격을 막을 수 없다.

## 실습 D: 질의와 인덱스 연결

```sql
SELECT id, title
FROM public.conversations
WHERE user_id = auth.uid()
ORDER BY updated_at DESC
LIMIT 1;
```

이 질의에는 `(user_id, updated_at DESC)` 복합 인덱스가 잘 맞는다. 먼저 사용자를 좁히고 그 안에서 최신 순서를 찾기 때문이다.
