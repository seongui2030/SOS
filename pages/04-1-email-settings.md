## 이메일 공급자 확인

Supabase Dashboard의 Authentication에서 Email 공급자가 활성화되어 있는지 확인한다. 꺼져 있으면 `Email logins are disabled`와 같은 오류가 난다.

`Confirm email`을 켜면 가입자가 받은 메일의 링크를 눌러야 로그인할 수 있다. 실제 서비스에서는 이메일 소유권을 확인할 수 있어 권장된다. 수업 중 빠른 실습을 위해 끌 수도 있지만, 운영과 학습 설정이 다름을 기록한다.

## 인증 메일 주소

메일 링크를 누른 뒤 돌아올 주소가 허용 목록에 있어야 한다. URL Configuration에 로컬과 실제 운영 주소를 등록한다.

```text
http://localhost:8080/**
https://sos-nu-flame.vercel.app/**
```

코드의 `emailRedirectTo`는 다음처럼 `/auth`를 가리킨다.

```ts
emailRedirectTo: `${window.location.origin}/auth`
```

## SMTP의 역할

Supabase 기본 메일 발송은 개발과 시험에 제한이 있을 수 있다. 실제 다수 사용자에게 안정적으로 메일을 보내려면 별도 SMTP 공급자를 구성하고 발신 도메인을 인증하는 방식을 검토한다. 메일이 오지 않을 때는 스팸함, 발송 제한, 이메일 주소 오타, Auth 로그를 확인한다.

## 기존 미인증 사용자

설정을 바꿨다고 기존 사용자의 확인 상태가 자동으로 바뀐다고 가정하면 안 된다. Authentication → Users에서 사용자를 열어 이메일 확인 상태를 본다. 개발용 계정은 관리 화면에서 확인 처리하거나 삭제 후 다시 가입할 수 있다. 실제 사용자의 계정을 임의 삭제하지 않는다.

## 보안과 사용자 경험

오류 메시지는 사용자가 다음 행동을 알 수 있어야 한다. `가입 완료`라고만 말하고 로그인 화면으로 보내면 인증 메일을 놓친다. `받은 이메일에서 인증 링크를 눌러주세요`처럼 구체적으로 안내한다. 비밀번호가 틀렸을 때 특정 이메일의 가입 여부를 지나치게 자세히 알려 주면 계정 존재 여부가 노출될 수 있으므로 운영 메시지는 신중히 설계한다.
