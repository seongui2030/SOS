## 실습 A: OAuth 이동 지도

종이에 앱, Supabase, Google 세 상자를 그리고 브라우저 화살표를 그린다. 각 화살표 위에 다음 정보를 적는다.

1. 앱 → Supabase: `provider=google`, 앱으로 돌아갈 `redirectTo`
2. Supabase → Google: Google OAuth Client ID와 callback
3. Google → Supabase: 승인 코드와 state
4. Supabase → 앱: 세션을 만들고 허용된 앱 주소로 이동

이 지도에서 Google이 앱으로 직접 세션을 주는 것이 아니라 Supabase가 중간 인증 서비스라는 점을 표시한다.

## 실습 B: 주소 비교표

```text
A. http://localhost:8080
B. http://localhost:8080/auth
C. https://YOUR_PROJECT_REF.supabase.co/auth/v1/callback
D. https://sos-nu-flame.vercel.app
```

- Google JavaScript 원본: A, D
- Google 승인 리디렉션 URI: C
- Supabase 앱 Redirect URL: B 또는 허용 패턴, D의 `/auth`
- 코드 `window.location.origin`: 로컬이면 A, 운영이면 D

주소를 복사할 때 끝 슬래시, 프로토콜, 포트가 설정 화면의 규칙과 맞는지 확인한다.

## 실습 C: 오류 카드 분류

다음 오류를 설정, 네트워크, 앱 로직 중 하나로 분류한다.

- `Unsupported provider`: Supabase 공급자 설정
- `redirect_uri_mismatch`: Google 주소 설정
- `ERR_CONNECTION_REFUSED localhost`: 돌아갈 서버가 없음 또는 잘못된 주소
- Google 로그인 후 conversations 404: 인증 이후 DB 연결
- 화면이 `/`와 `/auth` 사이에서 깜박임: 앱 리디렉션 로직

오류의 단계가 다르면 해결 장소도 다르다. Google 동의 화면까지 정상인데 DB 요청이 실패한다면 Client Secret을 새로 만드는 것은 관계없는 조치다.

## 형성평가

1. OAuth를 사용하는 서비스가 사용자의 Google 비밀번호를 받지 않는 장점을 쓰시오.
2. `redirect_uri_mismatch`를 해결할 때 비교할 두 주소는 무엇인가?
3. Site URL과 Google callback의 차이를 설명하시오.
4. `window.location.origin`을 사용하면 로컬·운영 코드가 같을 수 있는 이유는 무엇인가?
5. OAuth 성공 후에도 앱이 로딩될 수 있는 원인을 두 가지 쓰시오.
